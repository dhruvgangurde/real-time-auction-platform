## 2026-10-13 Phase 10 B1: backend for the room and landing (brief 12.6 B1)
- `placed_at_ms` comes from the script result: `accept()` in `_core.lua` returns the Redis TIME it already writes to the outbox as `accepted_at_ms`, and `place_bid.lua` copies it into its result, so the acknowledgement needs no extra read and automatic bids inherit their trigger's time. Arbitration logic is unchanged. Results stored by the previous script (up to `bid_request_ttl_s`, 600 s, after deploy) replay without it, so the field is null on such a replay.
- `reserve_met` in `bid_placed` is computed in the API from a reserve cached per process, next to the seller cache the bid path already reads before arbitration on the first bid of a live auction. Both are cached only from a live or closing row: the reserve is editable only while draft or scheduled, so a cached value never goes stale, and a scheduled-time bid attempt caches nothing. No Lua change; the acknowledgement is unchanged (the submitter learns `reserve_met` from its own `bid_placed`). `/live` computes it from the auction row it already loads; outside live and closing it reuses `closing.reserve_met`, so it matches `auction_closed`.
- Per-viewer fields `you_lead`, `your_max`, `your_result` are added to `/live` and `subscribed` only for an authenticated viewer. `your_result` is `won` for the settlement's winner, `lost` for anyone else who bid or armed a maximum on a sold auction, and null for no sale, cancelled or never took part (the room shows the no-sale and cancelled outcomes from `status` and `reserve_met`). `your_max` is null once maxima are deactivated at close or cancel (FR-51).
- `auction_started` is published by the scheduler right after activation, and by a repair step in every scheduler run for live auctions that started within the last hour and have no `started_sent` marker. The repair does not depend on missing live state, because a lazy rebuild (bid path, `/live`) can install the state after a failed activation install. The one-hour window is shorter than the 24 h marker, so an expired marker is never published again. A cancelled or closing auction is never announced.
- `X-Forwarded-For` is trusted only from the web proxy's fixed address on the `edge` network (`--forwarded-allow-ips=${WEB_PROXY_IP}`, default `10.201.0.10`), not from a subnet: the Docker gateway sits in every subnet and would make host traffic trusted. The api publishes no host port except 8010 in the development override, whose peer is untrusted. This assumes nginx is the outermost hop. **TBD-2 prerequisite:** behind a hosting load balancer or a TLS terminator in front of nginx, nginx must take the client address from that hop with `real_ip` (`set_real_ip_from` the balancer, `real_ip_header`) before it overwrites `X-Forwarded-For`; otherwise every client shares the balancer's address.
- The `web` service has no compose profile (brief 12.5 proposed one): it is the front door of the standard stack, so a plain `docker compose up --build` runs both api instances behind it (NFR-5). nginx does no `proxy_cache`: a shared cache keyed on the URL could answer a token-bearing request with an anonymous body; the per-instance micro-cache in the api already bounds reads. Round robin with a shared `zone`, so the workers alternate instances together.
- Read limits: anonymous `/live` and bid history 5 per second per client address (NAT trade-off: about ten polling tabs behind one address; configurable), and `/live` with a token 10 per second per user (`RATE_LIMIT_AUTH_LIVE_USER`), so neither path is unbounded. Both fail open on a Redis error, unlike every other limiter: refusing them would turn the read-only Postgres view of NFR-13 into a 503. Authenticated bid history is not limited (unchanged).
- The `/live` micro-cache serves anonymous requests only (no `Authorization` header). Authenticated requests always read fresh, so per-viewer fields are never cached and socket clients' refetches are never stale. Responses carry `Vary: Authorization`, so a browser never answers a token-bearing fetch with an anonymous body. A presented but invalid token stays a 401 (unchanged `optional_user`), never an anonymous read. The rebuild of missing live state is a single flight per auction per instance for every caller, cached or not.

## 2026-10-13 "Try to break it" is anonymous (deviation from NFR-21)
NFR-21 asks every state-changing endpoint to require the access token in a request header. That rule exists to stop a cross-site page from acting as a signed-in user whose cookie the browser sends along. `POST /api/v1/demo/stress` (design brief 12.4) has no user, no session and no cookie, so there is nothing to forge, and anyone can call it directly anyway; requiring sign-in would lose most of the visitors the demo is for. It stays anonymous and keeps the `X-Requested-With` header, so a plain cross-site form cannot trigger it. The controls are the single global run, a 60 s cooldown after the previous run settles, 3 starts per IP per hour, at most 50 bots and 20 submissions per bot, and an env kill switch.

## 2026-10-13 A seller cannot bid on their own auction
The SRS does not say whether a seller may bid on their own listing; accepting it allows shill bidding (a seller pushing the price up), which an end-to-end test showed was possible. `BidService` now refuses both a bid and a proxy maximum from the auction's seller with SELLER_CANNOT_BID (403 on REST, `bid_rejected` / `proxy_rejected` on the WebSocket), after input validation and before arbitration, so nothing reaches the live state or the outbox; the refusal is logged like any bid decision (FR-44). The seller of an auction never changes, so it is cached per process: only the first bid on an auction reads Postgres, and if that read fails the bid fails closed (SERVICE_UNAVAILABLE). The Lua arbitration is unchanged.

## 2026-10-13 The platform always keeps an active administrator (FR-75)
An end-to-end test showed an admin could suspend their own account, which locked out the only admin. Now: an admin cannot suspend themselves or remove their own admin role (CANNOT_TARGET_SELF, 409), and nobody (admin API or operator CLI) can suspend or demote the last active administrator (LAST_ADMIN, 409). "Active administrator" means the admin role and status active. Every change that can remove one takes a transaction-scoped advisory lock first, so two admins suspending or demoting each other at the same moment are decided one after the other and one of them is kept. The operator CLI gains `reinstate <email> --reason` (actor NULL, reason prefixed `cli:`) as the recovery path when no active administrator is left.

## 2026-10-13 Phase 9 payments and notification delivery
Decisions taken with the plan review:
- **No payment window in Release 1.** The SRS gives no window and no non-payment consequence, and its settlement state machine (B.5) has no transition out of pending_payment except to paid. An unpaid settlement stays payable; recorded as a known issue.
- **`auction_won` at close, alongside `payment_due`.** FR-70 lists the type and 4.10.2 S3 tells the winner both the outcome and that payment is due; UC-03 step 7 names only payment due. The requirement statement wins (CLAUDE.md section 2). This reverses the Phase 8 notification set; the closing tests changed with it.
- **`payment_failed` type** (migration 0010) for FR-68's "notify the bidder" of a confirmed failure.
- **100 paise minimum.** Razorpay cannot charge less (confirmed in the sandbox: 99 paise is refused with "Order amount less than minimum amount allowed", 100 is accepted). `POST …/payment` refuses a smaller settlement with AMOUNT_BELOW_GATEWAY_MINIMUM, and create and edit require `starting_price >= 100` in API validation (FR-12); no DB CHECK, so existing rows are untouched.
- **The platform captures authorized payments itself** in `sync_order`, so the Razorpay dashboard's auto-capture setting does not matter; "already captured" means read again.
- **Outbid rows through a task queued after the acknowledgement.** The outbox does not carry the outbid recipients: a `bid` entry holds only that bid's own bidder, amount, sequence and timing, and the displaced leader, exhausted maxima and immediately exceeded bidders exist only in the arbitration result (`BidResult.previous_leader` / `exhausted`). Rebuilding them in the persister would need trigger boundaries the outbox does not record. So `publish_bid_events` hands the same recipients as the live `outbid_notice` to `BidService.record_outbid` (production: a fire-and-forget Celery enqueue, `record_outbid`), inside try/except; arbitration and the acknowledgement are untouched. A lost enqueue loses the stored row only (known issue).
- **Email**: Mailpit (`axllent/mailpit:v1.27.10`, dev-only, in the override file) for development; any SMTP provider through `SMTP_*` for production; TBD-1 stays open. Verification and reset emails are queued to the worker (`QueuedEmailSender`), which closes the timing side channel and meets SI-4.

Design choices:
- **One payment row and one gateway order per settlement** (`idempotency_key = order:{settlement_id}`, receipt = settlement id, UNIQUE `gateway_order_id`). No database transaction is held across a gateway call; if the gateway refuses a duplicate receipt, the order found by receipt is adopted. The sandbox does not refuse duplicate receipts (live proof, 2026-10-13), so a start whose commit failed, or simultaneous starts, can leave unused extra orders at Razorpay; only the payment row's order is ever shown. A failed attempt is retried on the same order.
- **Exactly once** rests on the payment row lock (`FOR UPDATE` by gateway order id) taken by every source, with the conditional settlement update (which must change one row or the transaction rolls back), `UNIQUE gateway_payment_id`, the partial unique succeeded payment per settlement (from 0004) and the notification `dedupe_key` as backstops.
- **`payment_events` (append-only)** records each applied terminal outcome once, keyed `webhook:{event id}`, `callback:{payment id}:{outcome}` or `reconcile:{payment id}:{outcome}`; a sync that changes nothing writes no row. The same gateway payment's failure is applied once whatever the source.
- **The webhook trusts its signed payload** and makes no outbound call; it answers 200 once processed or deliberately ignored (unknown order, unsubscribed event, unreadable signed body) and 5xx on a database or limiter error so the gateway redelivers. Only `payment.captured` and `payment.failed` are acted on.
- **The checkout callback** verifies against the stored order id (the client's must equal it), then reads the order from the gateway; 202 pending when the gateway cannot be read.
- **Reconciler**: last activity (`updated_at`, touched when the winner reopens the payment) between 120 s and 7 days, least recently checked first (`reconciled_at`, nulls first), 50 per run.
- **Email delivery**: a group (user, type, auction) is due once its oldest pending row is older than 60 s; the claim (SKIP LOCKED, attempts + 1, a 5-minute lease) commits before sending; one email per group; backoff 1, 2, 4, 8 minutes, then failed and EMAIL_DELIVERY_FAILED. At least once across a crash. Rows written before 0010 are marked skipped and never emailed.
- **Live push**: producers publish a `notification` event after their commit; outbid rows are not pushed (the bid path's `outbid_notice` already was).
- **httpx** moved from the dev group to runtime dependencies (the gateway client); no Razorpay SDK.

## 2026-10-13 Revoking a role revokes every session (FR-6, FR-75, BR-1)
Roles travel in the access token (15 minutes). Before this, revoking a role changed Postgres but left the user's tokens valid, so a demoted admin kept full admin access until expiry: enough to re-grant itself admin through `PUT /api/v1/admin/users/{id}/roles/admin`, or to suspend the admin who demoted it; a demoted seller could keep creating, editing and publishing. Found by a security review of the Phase 8 commit.

Now every role removal, through the admin API or the CLI and for every role, revokes all of the user's sessions in the same transaction as the role change and its audit row, then uses the suspension mechanism: denylist keys for the sessions (retry, then the worker, then `sync_denylist`) and a `session_revoked` publish that closes open sockets with 4004. The old access token gets 401 `INVALID_TOKEN` on the next request, the refresh token is dead, and the user must log in again; the new token carries the remaining roles. The `role_revoked` audit row records actor, target, reason, before/after roles, the revoked `role` and `sessions_revoked`. The CLI now wires the same denylist fallback and socket notification as the API. A grant is unchanged: it takes effect at the next login and revokes nothing.

## 2026-10-13 Phase 8 closing, settlement and administration
- **Lock: `pg_try_advisory_xact_lock` inside the settlement transaction (FR-57).** The key is the first 8 bytes of the auction id as a signed 64-bit integer: stable across instances and versions. One-key advisory locks live in a different key space from the two-key proxy locks, so they never collide; two auctions sharing a key would only serialise. Not acquired means another closer is working: exit cleanly (`LOCKED`). Released at commit or rollback, so there is no lease to expire and nothing to leak. `UNIQUE(settlements.auction_id)` is the backstop (OR-14).
- **Drain first (FR-55, NFR-15).** Every close persists the auction's outbox with the ledger persister before deciding, so Postgres `end_time`, `extension_count` and the ledger are complete. If that fails the close is deferred and retried, never settled on a partial ledger.
- **Execution-time re-check (FR-58).** Inside the transaction: Postgres status closing, the outbox still empty, Redis status closing with Redis TIME >= `end_time_ms` (or no Redis state and Postgres `end_time` passed), and the Redis `sequence` not above the ledger maximum. Otherwise nothing is written (`NOT_ENDED` or `DEFERRED`). With D9 the end-time guard never fires; it is tested by forcing Redis state.
- **Outcome (FR-59, FR-60, BR-5).** Winner = highest amount, ties by lowest `sequence_no`. Reserve met or no reserve: `closed_sold` plus a `pending_payment` settlement with winner and final price. Otherwise, or with no bids: `closed_no_sale` plus a `no_sale` settlement with winner and price NULL (never payable). One settlement row per auction either way; `idempotency_key = settle:{auction_id}`.
- **One transaction for the outcome (FR-78).** Settlement, auction status with its audit row (actor NULL, before/after), a `settlement_created` audit row (FR-64: every settlement status transition is audited), every maximum deactivated (FR-51) and the in-app notification rows with `dedupe_key`. After the commit: Redis follows (closing to terminal), `auction_closed` is broadcast, and the live state is removed once the outbox is empty.
- **The settlement row is inserted before the status transition, with no row lock on the auction.** With the advisory lock bypassed, a second closer then blocks on the unique index and fails there, so the backstop test exercises the constraint itself; a row lock would serialise closers and make that test pass without the constraint. An IntegrityError on `uq_settlements_*` means "already settled": roll back, log, exit cleanly, no second notification set. Any other IntegrityError is a bug and is raised.
- **Trigger, retries, repair, alert (NFR-12).** The scheduler's `on_closing` hook enqueues `close_auction` (`acks_late`, 8 retries with backoff 1 s to 60 s; a deferred close is retried, then left to the sweep). `sweep_closing` (beat, 30 s) re-enqueues closing auctions without a settlement and settled auctions whose Redis state still says closing (a crash after the commit). Any auction in scheduled, live or closing past `end_time + close_grace_s` (300 s) logs `UNRESOLVED_CLOSE` at CRITICAL.
- **Force-close ends the auction now (FR-63).** `set_status.lua` gains a third mode, `end_now`: live to closing with no end-time condition, moving `end_time_ms` back to Redis TIME when it is later. Without it, the FR-58 re-check would refuse a force-closed auction (its end time is still in the future) on every run. Force-close then drains the outbox and writes the same instant to Postgres `end_time` (`original_end_time` untouched), so the record and any later Redis rebuild agree.
- **The persister applies an extension only with the insert of its bid.** A replayed batch (crash between commit and XDEL) no longer re-applies extensions: the transaction that inserted the row already applied it. Before, a stale replay finishing after a force-close could move `end_time` back past the forced instant. Found while designing force-close.
- **Seller notification types `auction_sold` and `auction_no_sale` (migration 0009, FR-62).** FR-70's list has nothing for the seller's outcome. The winner gets `payment_due` (`auction_won` stays unused); every other participant gets `auction_lost`, where participants are the distinct bidders in `bids` union the maximum holders in `proxy_bids`. Dedupe key `close:{auction_id}:{type}:{user_id}`. Payloads carry auction id, title, outcome, final price and `reserve_met`, never the reserve. The downgrade fails while rows of the new types exist instead of deleting them.
- **One `auction_closed` per auction.** Two callers may publish it: the one whose closing-to-terminal flip returned `OK`, and, when there is no live state, the one that settled. No live state can also mean another caller already flipped, published and removed it, so both go through `publish_closed_once.lua` (2026-10-13, from an end-to-end test that found a second broadcast; an administrator cancel goes through it too, via `Closer.broadcast_closed`, so a retried cancel also sends one): it sets the marker `closed_sent:{auction_id}` (`SET NX EX 86400`, outside the `auction:{id}:` prefix so live-state cleanup never removes it) and publishes in one atomic call; whichever comes second sends nothing. The guarantee is at most once per marker lifetime; clients apply `auction_closed` idempotently using `final_sequence_no`. The payload is built from the committed auction and settlement rows, never from live state. A Redis error during the broadcast is a warning with the correlation id (worker tasks log their task id as one); the close stays committed. A retry after full success sends nothing; a crash after the commit is finished, broadcast included, by the next run. If the process dies between the flip and the publish, that one event is lost (pub/sub is at-most-once) and clients see the outcome from `/live`. The field is `final_sequence_no`, equal to the last bid's sequence; clients always apply it (architecture.md section 4).
- **Admin flips are retryable.** Force-close and a cancel of a live auction flip Redis first, then drain, then commit Postgres. On a repeated call, `WRONG_STATUS:closing` (force-close) or `WRONG_STATUS:cancelled` (cancel) means "already flipped" and the call continues, so a failure between the flip and the commit is fixed by calling again. Meanwhile bids are refused.
- **Admin cancel (BR-9).** Draft, scheduled or live to cancelled with a reason; closing and terminal are `ALREADY_CLOSED`. No settlement and no notifications (no notification type exists for it). Its `auction_closed` carries `reserve_met` like every other payload: null only without a reserve, otherwise whether the committed price reached it, the value the auction detail shows (2026-10-13; it was null on every cancel before). Flipping Redis to cancelled resolves the earlier leftover where a cancelled auction kept a Redis `live` hash that cleanup could never remove.
- **Codes and audit.** Force-close of a draft or scheduled auction is `AUCTION_NOT_LIVE` (409); of a closing one it runs the close path. Reinstating an account that is not suspended is `NOT_SUSPENDED` (409). A force-close always writes an `auction_force_closed` audit row with reason and before/after, even when the scheduler moved the auction to closing a moment earlier (BR-12, NFR-14).
- **Settlement visibility (FR-64, BR-10).** `GET /api/v1/auctions/{id}/settlement`: the winner, the seller and administrators; the seller and administrators see the winner's id and name. Anyone else gets FORBIDDEN; NOT_FOUND before settlement.
- **Reinstate and the denylist (FR-76).** Reinstate sets the account active, audits it, then deletes `revoked:user:{id}`. `sync_denylist` now rewrites user keys only for users still suspended and deletes the key of anyone audited as suspended in the window but no longer suspended, which repairs a resync that raced the reinstatement. Suspension now also writes the revoked session keys, so a reinstatement never revives an old access token (before, these keys were written only by the 30 s resync).
- **Admin role changes reuse `UserService.change_role`.** It takes an email (CLI: actor NULL, reason `cli`) or a user id (API: actor and reason). Roles still travel in the access token (D6).
- **Worker and beat log the API's JSON lines (NFR-32).** Celery's `setup_logging` signal now calls `configure_logging`, so Celery no longer installs its own plain-text format, which dropped the `fields` of every worker log line (the `alert` and `auction_id` of `UNRESOLVED_CLOSE`, and of `LEDGER_WRITE_FAILED` since Phase 3). Found in the Phase 8 live run.

## 2026-10-12 Seller role on every seller write except cancel (BR-1)
Editing, publishing and adding or removing images require the seller role as well as ownership; before this, only creation checked the role, so a user whose seller role was revoked (D6) could still edit their auctions and publish their drafts after logging in again. Cancel stays owner-only, so a former seller can still withdraw a draft or scheduled listing (FR-18, BR-9). ## 2026-10-12 Phase 7 auction lifecycle and discovery
- **D1: `original_end_time` follows `end_time` until go-live (FR-14, FR-55).** FR-14 says it is set once at creation; but a seller may edit a draft or scheduled auction's end time (FR-17), after which the creation value would no longer be the scheduled end. Migration 0008 lets the trigger allow a change only while the auction is `draft` or `scheduled`; the service keeps the two equal on every pre-live edit; from go-live the field is frozen, so `end_time - original_end_time` is exactly the total soft-close extension. A deviation from FR-14's wording that keeps its purpose (auditable extensions).
- **D6: roles only through the operator CLI (FR-9, BR-1).** FR-9 forbids self-service role changes. `python -m app.cli grant-role|revoke-role <email> <role>` and `seed-categories`; each change and its `audit_log` row (actor NULL, reason `cli`, before/after roles) commit in one transaction. Roles travel in the access token, so the CLI tells the user to log in again. Admin role endpoints are Phase 8.
- **D7: `auctions.current_price` and `bid_count` (FR-19, FR-23).** Nullable BIGINT and INTEGER, kept by the persister in the same transaction as the ledger insert, from the highest newly inserted sequence, never decreasing (a `CASE` against the old `bid_count`, so out-of-order batches are harmless); backfilled from the ledger by migration 0008. Price filters use `coalesce(current_price, starting_price)`. Live and closing items in lists, the watchlist and the dashboard show the Redis values, which may be a few seconds ahead.
- **D8: "a bid exists" means Redis `sequence > 0` (FR-17, BR-4).** Bids may be accepted but not yet persisted, so the ledger cannot answer. Missing live state is rebuilt first; if Redis cannot answer, a live edit is refused with `SERVICE_UNAVAILABLE` (fail closed). The check and the write are not atomic (see currentstate known issues); only title, description and images can change on a live auction, so pricing is never at risk.
- **D9: live -> closing only through `set_status.lua` (FR-16, FR-58).** An atomic check-and-set at the bid serialisation point that flips the Redis status only once Redis TIME has reached `end_time_ms`. Candidates come from Postgres (`end_time <= now()`), which lags Redis and never leads it; an auction extended past its Postgres end time stays live. Postgres follows with a conditional UPDATE and its audit row; a Redis-closing / Postgres-live pair is completed by the next run. B.4 has no closing -> live transition and none is needed: once Redis says closing, no bid can extend the auction.
- **D10: images on a local named volume (`media`) behind a three-method storage interface, Pillow for re-encoding (SI-5, NFR-24).** The type is what Pillow decodes; `Image.MAX_IMAGE_PIXELS` is set to `image_max_pixels` and its bomb warning raised as an error, so an oversized image is refused from its header; the image is verified, reopened, orientation applied and re-encoded with no metadata; names are server-chosen (`auctions/{id}/{uuid}.{ext}`); `/media` is served read-only. The upload is the raw request body (no multipart dependency), read as a stream with a 5 MB cap. The file is saved before the commit and deleted if the commit fails, so there are no orphan files.
- **Scheduler (FR-15, FR-16).** Beat every 5 s; three idempotent steps (activate, repair, close) safe under concurrent runs: `FOR UPDATE SKIP LOCKED` and conditional UPDATEs give one transition and one audit row each. Activation commits Postgres first and only then installs the live state, so Redis never says live before Postgres; bids in between are rebuilt lazily by the bid path. A start more than two intervals late is activated with a warning (FR-16). `on_closing` only logs until Phase 8.
- **Listing (FR-22, FR-23, FR-30).** Default statuses are scheduled, live and closing; closed ones only when asked for; drafts and cancelled auctions are never listed. Search uses `websearch_to_tsquery('simple', q)` ranked by `ts_rank` over the A/B weighted vector (title above description). Page and page size (20, at most 50), ordered by rank, `created_at`, id so pages are stable.
- **Per-field validation errors (FR-12).** The envelope gains an optional `fields` object; the pydantic handler fills it for every invalid field. `code` and `message` are unchanged.
- **Status codes for lifecycle actions.** Edits and image changes on closing, closed or cancelled auctions give `ALREADY_CLOSED`; publish or cancel of a live or closing auction `AUCTION_ALREADY_LIVE`; publish of a scheduled auction `NOT_DRAFT`. "Start not in the past" (FR-12) is checked when the start time is set and again at publish, so a scheduled auction about to start can still have its title fixed. An auction that has left draft keeps at least one image (FR-13). Cancel is owner-only for now; an administrator cancel with a reason comes with the Phase 8 admin work.
- **Bid history (FR-27, BR-10).** Keyset on `sequence_no`; for live and closing auctions the outbox is merged up to the state's sequence (same MULTI read as the snapshot); admins also see bidder ids. The seller's view of the winner's identity (BR-10) needs a settlement, so it is Phase 8.

## 2026-10-12 Phase 6 fix pass (from docs/audit-phase6-7.md)
- **D2: only live and closing auctions have Redis state (FR-15, FR-26, FR-30, DC-1, FR-43).** `/live` and `subscribe` serve every other status from Postgres (`degraded: false`) and write no Redis key except presence; `init_live_state` raises `AuctionNotLive` for any other status, so nothing can create such state. Reason: a `scheduled` hash created by viewing was never refreshed, and the auction kept rejecting bids after going live. Each reconciliation run also removes state left for auctions Postgres no longer calls live or closing; `cleanup_state.lua` re-checks inside Redis and keeps any hash whose own status is live, closing or rebuilding, or whose outbox is non-empty, so racing an activation or a rebuild never deletes state in use.
- **D3: one socket per session (CI-3).** The newest socket of a session wins: registering takes a generation from a global counter (`ws_claim.lua`), older sockets of that session close with **4012 SESSION_REPLACED** at once on the same instance and through `session_replaced` on the user channel elsewhere; the higher generation always wins, so simultaneous opens are deterministic. A user may hold at most 5 sessions (`ws_max_sessions_per_user`); a held session may always reconnect. Re-authenticating a socket requires a token of the same session (a refreshed one); another session's token closes 4002. Client contract: never auto-reconnect after 4002, 4004 or 4012.
- **D4: no idle timeout for authenticated sockets (FR-29, FR-30 spectating).** Close code 4011 is retired. Dead peers are dropped by the protocol keepalive (uvicorn `--ws-ping-interval 20 --ws-ping-timeout 20`), which browsers answer without application code; a quiet spectator is never closed. The 5 s authenticate timeout stays.
- **D5: deviations recorded.** FR-29 says "any number of auction rooms"; a connection may hold at most 20 (`ws_max_subscriptions`), a resource bound no realistic client reaches. FR-44 says the bid limit is "configurable per auction"; it is one platform-wide setting (`rate_limit_ws_place_bid`, default 10 per second), because nothing in the SRS gives anyone a way to set it per auction.
- **D11: WebSocket subscribe fails closed during a Redis outage (NFR-13, FR-42).** Its per-user rate limit needs Redis, and without Redis there is no pub/sub to deliver room events anyway. `GET /live` stays available from Postgres with `degraded: true`, which is what NFR-13's read-only viewing needs.
- **D12: strikes (CI-3, DC-11).** Invalid frames, RATE_LIMITED, FORBIDDEN and NOT_SUBSCRIBED each count one strike; SERVICE_UNAVAILABLE never does (the fault is ours, and the client is told to retry). One strike is forgiven per 60 s (`ws_strike_decay_s`); 5 strikes close 4009.
- **Message limits (CI-3, FR-44, NFR-22).** Every frame first counts against a per-connection cap kept in memory (30 per second, no I/O), then a per-user, per-type limit in Redis for all six types: `place_bid` 10/s, `set_proxy` 5/s, `subscribe`, `unsubscribe`, `authenticate` and `ping` 20/s each, so bid submission is the strictest. With the limiter unreachable, `place_bid`, `set_proxy` and `subscribe` fail closed; `authenticate`, `unsubscribe` and `ping` proceed, still bounded by the in-memory cap. Bids then re-check the denylist, the bidder role, the room subscription and degraded mode; `subscribe` re-checks the denylist too (FR-6 "every WebSocket message").
- **Server-generated connection ids (NFR-32).** The connection id used for presence and session bookkeeping is a server UUID; the `X-Request-ID` a client may send stays a log correlation id only. A shared header value previously merged connections and bypassed the per-user limit.
- **Unexpected errors are answered, logged and never swallowed (NFR-32, FR-42).** An error in one message is logged with its traceback; a bid not yet acknowledged gets `SERVICE_UNAVAILABLE` (outcome unknown, retry with the same request_id), any other message gets `error INTERNAL_ERROR`, and the socket stays open. An error in a connection task closes 1011 and logs at ERROR. The close log line reports the real code (the server's, the client's, or 1006 when the connection was lost).
- **FR-44 log line for every bid decision.** `log_bid` and `log_proxy` in `services/bidding.py` are called by arbitration, by the WebSocket gate (refusals before arbitration) and by the REST limiter refusal; lines carry `automatic_sequence_nos`. Proxy lines never carry the maximum (FR-51).
- **Reconciliation guards each auction (FR-43, NFR-10).** Only `kind=bid` outbox entries count as pending; any error for one auction raises the `RECONCILE_FAILED` alert and the run continues with the others.
- **Snapshot consistency (FR-26, CI-6).** State, outbox and presence are read in one MULTI; ledger bids above that state's sequence are left out, so `recent_bids` never runs ahead of `current_price`. Client rule: buffer room events received before `subscribed` and apply only those above `snapshot.sequence_no`.
- **Hub resubscribe (CI-7).** After a pub/sub reconnect the hub subscribes until no referenced channel is missing (a room joined while SUBSCRIBE was in flight included), and only then reports `degraded: false`.
- **Soft-close audit rows carry `before` (FR-77):** `{end_time_ms, extension_count}` read under a row lock, chained in sequence order within a batch.

## 2026-10-12 Phase 6 real-time layer choices
- **One hub per instance, reference-counted pub/sub.** An instance subscribes to a room or user channel only while it has a local socket there, so fan-out cost follows local interest (NFR-30). Each socket has a bounded queue; overflow closes it with 4008 instead of slowing the hub (NFR-5).
- **Acknowledge, then publish.** The ack goes on the submitter's own FIFO queue before any publish, so the submitter sees its ack before its own `bid_placed` (FR-40, NFR-3). The REST fallback publishes in a background task after the response.
- **Sequence numbers on every room event, at-most-once delivery accepted.** Pub/sub can lose or reorder events across instances; clients order by `sequence_no`, drop duplicates, and refetch `/live` on a gap, on `presence.sequence_no` ahead of them, or after recovery from degraded mode. Retries republish on purpose: a retry after a timeout publishes what the first attempt never did.
- **Presence carries `sequence_no` and `end_time_ms`** so a quiet room detects a lost `bid_placed` within one presence interval (FR-32).
- **Degraded mode** is per instance: lost pub/sub means `system_status {degraded: true}`, bids rejected with `SERVICE_UNAVAILABLE`, and `degraded: false` only after every referenced channel is resubscribed. The pub/sub client has no transparent retries so a dropped connection surfaces.
- **Outbid recipients** are the previous leader, every exhausted maximum, and every bidder whose bid in the same trigger was immediately exceeded (e.g. a manual bid answered by a proxy), minus the new leader, each once. The last group extends the agreed rule; without it a bidder outbid by a proxy response gets no notice (UC-01 post-condition).
- **Lua returns `previous_leader` and `exhausted`** under `_internal` for addressing notices only; the service strips them and payloads are built field by field. No decision, sequence or outbox entry changed.
- **Pseudonyms** are `Bidder-` + 4 hex of HMAC-SHA256 with `ALIAS_SECRET` (NFR-27); collisions within one auction are possible (65,536 values) and accepted as display-only.
- **Origin allowlist** applies when an Origin is present; a missing Origin (non-browser client) is allowed because a token is still required.
- **Room membership is required for WS bids** (FR-34, `NOT_SUBSCRIBED`); the REST fallback cannot hold a subscription and skips only that check. Both require the bidder role (FR-7).
- **Session revocation reaches sockets two ways:** `session_revoked` on the user channel closes them on every instance, and every bid re-runs the denylist check, so a lost broadcast still denies the next action (FR-6).
- **`/live` falls back to Postgres** with `degraded: true` when Redis is unreachable, so viewing stays available read-only (NFR-13); its end time may then lag (see the FR-58 note).
- **Tests run two real uvicorn servers inside pytest** with independent hubs on one Redis, driven by real WebSocket clients; `create_app()` gained a lifespan and dependencies come from overridable providers.
- **`auction_test` is created once per pytest session.** The `test_db` fixture is registered in two conftests; recreating it twice killed earlier connections.

## 2026-10-12 Identity before WebSockets (roadmap phases 5 and 6 swapped)
The WebSocket layer authenticates its first message with the access token (CI-4, FR-5) and needs `current_user`, the denylist check and the session model, so Identity is built first. Roadmap Phase 5 is now Identity and Phase 6 the real-time layer.

## 2026-10-12 Identity choices
- **`EMAIL_TAKEN` on duplicate registration** (FR-1 says so), even though it reveals that an address is registered. Non-enumeration is applied where the SRS requires it: login (FR-4), resend-verification and forgot-password (FR-8).
- **argon2id** via argon2-cffi with t=3, m=64 MiB, p=4 from config; hashing and verification run in a worker thread. An unknown email verifies against a real throwaway hash so timing matches a wrong password.
- **Password rules:** minimum 10 (FR-2), maximum 128, not equal to the email, new users get the bidder role (the SRS is silent on the last three).
- **Access tokens are HS256 JWTs, 15 min**, with `sub`, `roles`, `sid`, `iat`, `exp`, `jti`; decode pins the algorithm and requires every claim. Expiry is checked against the injected service clock, not the JWT library's wall clock, so tests control time. Roles in the token are up to 15 minutes stale; role changes are out of scope until the admin work.
- **Refresh tokens** are opaque, hashed at rest, cookie-only (`HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`), 30 days sliding, rotated on use (NFR-17). Refresh requires `X-Requested-With` as CSRF protection (NFR-21). Logout requires a valid access token.
- **Denylist with Postgres fallback.** Per-sid keys for logout and reset, a per-user key only for suspension (a user key after reset would block the user's next login for 15 min). Writes retry once, then go to a Celery task, and the `sync_denylist` beat task rewrites recent revocations from Postgres every 30 s; a failure of both write and enqueue raises the `DENYLIST_WRITE_FAILED` alert. On a Redis error at request time the check runs against Postgres and is never skipped (FR-6).
- **Rate limits are fixed windows keyed by the clock bucket**, so a limit resets when the clock enters the next window and tests advance a fake clock instead of sleeping. They fail closed (`SERVICE_UNAVAILABLE`) when Redis is down: a limiter that stops counting is no brute-force protection, and bidding already fails closed without Redis.
- **Console email backend is dev-only** (TBD-1 open): it logs the whole message including links with raw tokens, and `check_startup_config()` refuses it outside `APP_ENV=local`, as it refuses a `JWT_SECRET` under 32 bytes.
- **Unauthenticated token endpoints are rate limited per IP** (reset 10/h, verify 20/h), and reset validates the token with a SELECT before the 64 MiB argon2 hash, so bogus tokens cannot be used to burn memory and CPU. The single-use `UPDATE ... WHERE used_at IS NULL` still runs after hashing and decides races.
- **Bid history uses a keyset cursor** (`created_at_ms:id`), newest first (FR-10), on the existing `(bidder_id, created_at DESC)` index.
- **No `X-Forwarded-For` handling yet.** Rate limits use the direct peer address; a reverse-proxy deployment must add trusted-proxy handling first. (Superseded 2026-10-13 by Phase 10 B1: trusted from the web proxy's fixed address only.)

## 2026-10-12 Phase 4 proxy bidding choices
- **`arm_seq` is a counter at the serialisation point, not a timestamp.** Every set or raise does `HINCRBY arm_seq` and stores `max|arm_seq`; equal maxima are won by the lower `arm_seq` (FR-49). Redis TIME can tie at microsecond resolution and a rebuild cannot reproduce it; a counter is exact, ordered by the same atomic step that orders bids, and rebuilds from Postgres (restarting above the highest `arm_seq` ever persisted). **A raise takes a new `arm_seq`:** the tie goes to whoever committed to that amount first, so raising resets priority.
- **Automatic bids may be sub-increment** (FR-48 caps at the maximum, FR-49 lets the leader stop at its own maximum). A maximum of 300 facing a manual 295 at increment 10 bids 300. The SRS wins over the earlier "below the next minimum bid places nothing" wording.
- **Exhaustion rule, one rule only:** after every resolution, a maximum whose owner is not the leader and that no longer exceeds the highest bid is deactivated (UC-02 5a). The leader's own maximum stays armed even when it sits at its own maximum. Phase 9 uses the `proxy_deactivated` outbox entry for the outbid notification.
- **A manual bid equal to an armed maximum wins** (FR-48: a maximum acts only when it *exceeds* the highest bid). The proxy places nothing and is deactivated. The eBay-style "earlier commitment wins" would need the manual bid rejected at arbitration with a code the SRS does not define.
- **Lowering or setting an equal maximum is rejected** with `PROXY_CANNOT_DECREASE`. FR-46 forbids lowering; the SRS is silent on equal, and an equal value changes nothing a bidder could want, so it is treated as a client error rather than a silent no-op.
- **Any non-live auction gives `AUCTION_CLOSED` for a maximum** (FR-46, UC-02 2b), including a scheduled one, unlike manual bids which distinguish `AUCTION_NOT_STARTED` (FR-36).
- **Closed-form resolution, at most two automatic bids per trigger.** The runner-up's bid at its own maximum is recorded first when it is a valid bid below the winner's target, then the winner bids once at `min(own max, competing + increment)`. Never a per-increment loop. With equal maxima the runner-up's record bid would equal the winner's price and is skipped, so ledger amounts stay strictly increasing.
- **Privacy under FR-49 (second-price property).** The final price inherently reveals the runner-up's level, and the record bid at the runner-up's maximum discloses nothing beyond that. BR-7 protects the leading maximum, which is never bid at; `test_proxy_privacy.py` asserts that value appears nowhere except its owner's own result. Proxy log lines carry no amount; `audit_log` holds no proxy amounts.
- **Shared Lua core via a load-time include.** `place_bid.lua` and `set_proxy.lua` contain `--#include _core`, expanded by `app/lua/__init__.py` from `app/lua/_core.lua` (state loading, `accept()`, `resolve()`). One source of truth, and `SCRIPT LOAD` still sees one script per entry point.
- **Proxy rows in Postgres.** `proxy_bids.arm_seq` (migration 0007). The persister applies `proxy_set` only when its `arm_seq` is above every row ever persisted for that (auction, bidder), active or not, under `pg_advisory_xact_lock(hashtext(auction), hashtext(bidder))`, so a stale replay held by a concurrent persister can never resurrect a deactivated maximum; `proxy_deactivated` flips only the row with its own `arm_seq`. No `audit_log` rows for proxy changes: FR-77 does not list them and they must not carry amounts.
- **`hypothesis` property test with `derandomize=True`:** 200 random op sequences through the real scripts, compared step by step with a pure-Python reference model (`tests/bidding/proxy_model.py`). The fixed seed keeps CI deterministic; the table-driven cases (hand-computed, 49 cases across increments 1, 50 and 1000) are the known-correct oracle (OR-13).

## 2026-10-12 Phase 3 bid arbitration choices
- **Outbox stream.** Accepted bids are appended by the arbitration script to a per-auction Redis stream in the same atomic step. The persister deletes entries only after the Postgres commit, so a bid is never acknowledged without being either in the outbox or in the ledger (NFR-10). This replaces "fire a task and hope": a lost Celery message or a crashed worker only delays persistence.
- **Redis AOF `everysec` and `noeviction`.** AOF shrinks the window of acknowledged-but-unpersisted bids that a Redis crash can lose to about one second. `noeviction` means live state and outbox entries are never silently dropped under memory pressure: writes fail and the bid path fails closed instead (FR-42, BR-14). Scripts start with `#!lua` so Redis refuses the whole script under OOM rather than failing midway through its writes.
- **Request dedupe scoped by bidder.** The idempotency key is `auction:{id}:req:{bidder}:{request_id}`, not just `request_id`, so two bidders who happen to reuse a client request id can never receive each other's result. Only acceptances are stored (10 min TTL); rejections write nothing.
- **Extension rule.** FR-53 says "extend the end time by the configured extension amount, evaluated against the then-current end time", so the new end is `end_time + extension`, not `now + extension`. It is unambiguous; recorded here because the user asked for an explicit choice.
- **Acknowledge before persist.** `place_bid` returns as soon as the script has decided (FR-40). The Celery enqueue runs in the event loop's executor and is not awaited; an enqueue failure is logged and the beat sweeper persists the bid anyway.
- **Self-outbid policy is a platform environment flag** (`SELF_OUTBID_POLICY_ENABLED`, default true), copied into each auction's live state at init. FR-38 says "where the policy is enabled" but gives nobody the power to set it per auction; a column can be added if the product later wants it.
- **`starting_price > 0`** (migration 0006). FR-37's limit is 100 x the starting price; with a zero start price every bid would be `BID_ABOVE_LIMIT`. Tightening the CHECK keeps FR-37 literal.
- **Script numbers are strings.** Lua numbers are doubles and cjson keeps 14 significant digits, so the script receives amounts as decimal strings, writes integers back with `%.0f`, and returns every number as a string. The service validates amounts are integers <= 2^53-1 before calling Redis.
- **Rebuild uses a `rebuilding` status with a token and lease.** `init_state.lua` writes the snapshot as `rebuilding`; `place_bid.lua` treats that as not initialised; the service re-checks the ledger max and only then commits via `finalize_state.lua` (token-guarded). A crashed rebuild is taken over after its 5 s lease. Two concurrent rebuilds cannot clobber each other.
- **Rebuild refuses while the outbox is non-empty.** A snapshot taken then would miss accepted bids. The caller fails closed with `SERVICE_UNAVAILABLE`; the sweeper drains the outbox within seconds.
- **`SEQUENCE_COLLISION` keeps the bid.** If an outbox entry's sequence already exists in the ledger with different data (Redis reissued a number after losing writes), the entry is written to `audit_log` (action `sequence_collision`) in the persister's transaction and copied to `auction:{id}:bids:dead` before deletion. Nothing is lost; an operator decides.
- **Reconciliation checks every number in 1..sequence**, not just the ledger max against the Redis sequence, and also alerts `SEQUENCE_REGRESSION` when the ledger is ahead of Redis. Read order (sequence, outbox, ledger) means a concurrent persister can never cause a false gap.
- **Postgres `auctions.end_time` lags Redis** by up to the sweep interval, because extensions reach Postgres only through the persister. Redis `end_time_ms` is authoritative while live. Phase 7 and Phase 8 must not decide "ended" from Postgres alone (FR-58).
- **Client contract.** `SERVICE_UNAVAILABLE` after a timeout means the outcome is unknown; clients retry with the same `request_id`. Phase 5 and Phase 10 must implement this.
- **Tests use Redis DB 15** and the existing `auction_test` database, with committed rows (the persister, scripts and rebuild use their own connections). The concurrency test has 20 bidders on 20 separate connection pools race to 500 accepted bids (about 5,000 submissions), each bidding exactly the reported minimum next amount.

## 2026-10-12 Phase 2 schema choices
- **Primary keys.** UUID (`gen_random_uuid()`) for users, auctions, settlements, payments and sessions, because these IDs appear in URLs and events and should not be guessable or reveal volume. BIGINT identity for high-volume or internal tables: bids, audit_log, notifications, auction_images, proxy_bids, categories and the token tables.
- **Payments allow retries.** `payments.settlement_id` is not unique. A partial unique index allows at most one `succeeded` payment per settlement, so a failed attempt can be retried. This differs from the SRS ER model (B.2), which says a settlement "has at most one Payment". FR-67 and DC-5 are met by the unique `gateway_ref` and `idempotency_key`, and the requirement statements win over the diagram.
- **`bids.end_time_after`** stores the auction end time after a bid that triggered a soft-close extension, so FR-55's "persist the updated end time alongside the bid" holds without touching `original_end_time`.
- **`original_end_time` immutability** is enforced by a `BEFORE UPDATE OF original_end_time` trigger that raises `check_violation`, not only by code (FR-14).
- **Sessions table** stores hashed refresh tokens with `revoked_at`, so logout and suspension revoke immediately (FR-6).
- **`notifications.dedupe_key`** is UNIQUE so a retried dispatch cannot create a second notification (DC-5).
- **Owner/app role split.** Alembic runs as the owner via `MIGRATION_DATABASE_URL`. api, worker and beat run as `auction_app` via `DATABASE_URL`. Migration `0005` creates the role if missing, always re-applies its password from `APP_DB_PASSWORD`, and grants per table. The app role gets SELECT only on `alembic_version`, so it can never change migration state. There are no default privileges, so every future migration that adds a table must grant on it explicitly. Downgrade revokes all grants but keeps the role, because roles are cluster-wide and shared with the test databases.
- **`migrate` compose service.** A one-shot service runs `alembic upgrade head` before api, worker and beat start (`service_completed_successfully`). Without it a clean `docker compose up --build` would leave readiness at 503, because the app role only exists after migration `0005`.
- **Full-text search** uses the `'simple'` text search config (no stemming), because titles are product names and listings may mix languages.
- **`alembic check`** reports no drift on the generated `search_vector` column, the `lower(email)` index or the partial indexes, so nothing is excluded from autogenerate comparison.
- **`proxy_bids.armed_at` semantics are not decided yet.** Whether raising a maximum resets `armed_at` matters for FR-49's equal-maxima rule and is decided in Phase 4.
- **DB integration tests** use their own databases: `auction_test`, created and migrated once per session, and `auction_migtest`, created and dropped inside the migration-cycle test. Dev data and shared test tables are never wiped.
